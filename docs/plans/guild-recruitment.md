## Approved scope and EARS requirements

- REC-016: WHEN a compatible Java player supplies private recruitment input, THE SYSTEM SHALL use a native dialog and accept callbacks only for that player, current input and navigation session, once and within two minutes; older/unknown clients SHALL retain private chat fallback. Private application details and guild guides SHALL open paged books on Java and native forms on Bedrock. Return callbacks SHALL reauthorize the current screen. Listings SHALL expose language/play-time filters and edit time without changing membership or fees; older records SHALL display unknown freshness. Actual client acceptance, TEST activation, merge and production rollout remain explicit gates.

- REC-015: WHEN an authorized editor starts guided setup, THE SYSTEM SHALL keep draft changes in session memory until preview and explicit publication, require Discord invite/instructions for Discord mode, and preserve current joining fees. Cancelling SHALL leave the published profile unchanged. WHEN recruiters review an application, THE SYSTEM SHALL show submission/expiry and confirm approval/decline before invoking the existing reauthorized service. Existing private application tracking remains available and receives clearer timing labels. No production or TEST activation is authorized by this implementation request. Project-local SPEAR helpers remain absent; this record tracks requirements and verification manually.

- REC-014: WHEN recruitment opens for a member, THE SYSTEM SHALL offer listing preview and authorized management controls; guildless players SHALL open browsing. WHEN browsing, THE SYSTEM SHALL expose recruiting, beginner, Building, PvP and Discord filters, reset and three sort orders. Profile/back navigation SHALL preserve the board page; filter resets and searches SHALL return to the first page. Java SHALL retain a nine-column inventory with a quick-filter row, 36 listing slots, page count and conditional arrows; native Bedrock forms SHALL expose the same choices. Existing permissions and admission semantics remain unchanged. Discord mode missing setup SHALL explain the missing invite/instructions rather than imply a permission failure. The supplied pack's real registered icon IDs replace nonexistent IDs. No project-local EARS/state helper is available; this document records the manual state. Preview is a browser simulation with real pack backgrounds/icons; vanilla guild banners, player inventory and Minecraft fonts require client acceptance.

- REC-013: WHEN a player opens a guild profile or joining confirmation, THE SYSTEM SHALL render the guild banner through the same display resolver as its board entry, preserving patterns and removing pack model overrides. Player screenshot showed a missing custom texture after opening the profile; source inspection found the profile omitted the guild payload and used `lg_banner` instead. Both profile and confirmation now carry the guild payload. No layout or controls changed; the existing interactive recruitment preview remains a simulation, and Minecraft resource-pack acceptance requires retesting after deployment.

- REC-001: WHEN a rank is granted Manage Recruitment, THE SYSTEM SHALL permit recruitment invites and application review without granting kicks, promotions or rank editing. Existing Manage Members invite access SHALL remain compatible. Leaders retain implicit access.
- REC-002: WHEN a rank is granted Edit Recruitment Settings, THE SYSTEM SHALL permit listing/mode/requirements/Discord edits independently of application review.
- REC-003: WHEN a player opens /g lfg, /g browse or /g recruitment, THE SYSTEM SHALL open the same searchable recruitment board with profiles, slots, fees and joining methods.
- REC-004: WHEN an existing guild has no recruitment profile, THE SYSTEM SHALL interpret its open flag as Join Immediately or Closed without changing its fee.
- REC-005: WHEN recruitment is Apply In Game, THE SYSTEM SHALL accept at most one active application per player/guild and three per player, with configurable limits and seven-day default expiry.
- REC-006: WHEN a recruiter accepts an application, THE SYSTEM SHALL create a 48-hour default join offer and record the actor; it SHALL NOT enroll or charge the applicant until explicit confirmation.
- REC-007: WHEN an applicant confirms an offer, THE SYSTEM SHALL recheck identity, membership, current capacity, current fees and current eligibility before using canonical admission/payment; uncertain payment outcomes SHALL NOT be retried automatically.
- REC-008: WHEN an applicant withdraws or joins a guild, THE SYSTEM SHALL withdraw the application or close other active applications respectively; application answers SHALL be private to the applicant and authorized recruiters.
- REC-009: WHEN a guild uses Discord applications, THE SYSTEM SHALL require a valid HTTPS Discord invite and instructions, show the exact destination before leaving the game, and never infer application submission or acceptance from opening a link. Java receives a clickable link; Bedrock receives a copyable invite.
- REC-010: WHEN a player without a guild completes onboarding, THE SYSTEM SHALL send one non-interrupting recruitment prompt; optional periodic reminders SHALL respect a personal opt-out and configurable interval. Leaving a guild SHALL provide a quiet browse shortcut.
- REC-011: WHEN recruitment is deployed, THE SYSTEM SHALL support spawn NPC/hologram discovery through the same board command; placement/configuration is an operator integration, not automatic world mutation.
- REC-012: WHEN recruitment is changed, THE SYSTEM SHALL provide a responsive private clickable preview and distinguish simulation, local proof, hosted CI and in-game acceptance.
